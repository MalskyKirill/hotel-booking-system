# Hotel Booking System: запуск в Postman

В этой папке находятся коллекция из 68 запросов и окружение для локального запуска.
JWT, ID, requestId, даты и данные для регистрации коллекция получает сама.

## Как запустить на Mac

1. Подними приложения из IDEA в порядке: **Discovery → Hotel → Booking → Gateway**.
   У Hotel и Booking должен быть активен профиль `demo`; настрой ключи RSA по README проекта.
   `api-support` и `request-context` — библиотеки, отдельно их запускать не нужно.
   Дождись готовности Gateway на `http://localhost:8080`.
2. В Postman нажми **Import** и импортируй оба JSON из этой папки:
   - `HotelBooking.postman_collection.json`;
   - `HotelBooking.local.postman_environment.json`.
3. Выбери окружение **Hotel Booking — Local** в правом верхнем углу.
4. Открой это окружение и укажи текущие локальные значения:

   | Переменная | Что указать |
   | --- | --- |
   | `adminPassword` | Значение `DEMO_ADMIN_PASSWORD` из конфигурации запуска Booking в IDEA |
   | `userPassword` | Значение `DEMO_USER_PASSWORD` из той же конфигурации |

   Имена уже заданы: `demo-admin` и `demo-user`. Если ты менял их в настройках приложения,
   исправь `adminUsername` и `userUsername`. При другом порте Gateway исправь `baseUrl`.
5. Открой коллекцию **Hotel Booking System — полный последовательный прогон** → **Run**.
   Выбери все семь папок, оставь исходный порядок и **1 iteration**, нажми **Run**.
   Если Runner показывает выбор окружения, проверь, что выбрано **Hotel Booking — Local**.

Рекомендуется актуальный Postman Desktop. Для Postman в браузере потребуется Desktop Agent,
чтобы обращаться к localhost. Сценарий рассчитан на Collection Runner: запуск отдельных
запросов кнопкой Send не создаёт общий контекст прогона.

## Что проверяется

- Swagger/OpenAPI через Gateway, вход и регистрация, ответы без пароля.
- JWT и роли USER/ADMIN, скрытие внутреннего API, валидация запросов.
- Создание, чтение и изменение отелей и номеров, недоступные номера и рекомендации.
- Ручное бронирование, повтор по requestId, конфликт параметров и отмена пересекающейся брони.
- Автоподбор свободного номера, история и пагинация, доступ только владельцу брони.
- Статистика загрузки и счётчики, отмена и повторная отмена, освобождение номеров.
- Защита записей с историей от удаления и CRUD временных записей без истории.

Ответы **400, 401, 403, 404 и 409** в соответствующих запросах ожидаемы: смотри результат
вкладки Tests, а не только HTTP-код. При неожиданной ошибке коллекция останавливается.
При ответе 202 она опрашивает состояние раз в секунду до 90 секунд и проверяет итоговый статус.

## Повторный запуск и тестовые данные

Каждый полный запуск создаёт отдельного пользователя, собственный отель и номера с уникальными
именами. ID существующих записей не используются для изменения или удаления. В конце сценарий
отменяет свои бронирования и удаляет дополнительные записи без истории.

Пользователь с историей, основной тестовый отель, его номера и три отменённые брони остаются
в базе: правила проекта защищают историю от удаления. Повторный запуск создаёт новый набор
данных и не требует сбрасывать H2. Если прогон остановился раньше конца, часть его данных и
бронирований может остаться; следующий полный запуск всё равно использует новые данные.

JWT и сгенерированные пароли сохраняются в локальных переменных одного прогона.
В поставляемом окружении оба demo-пароля пустые. Не публикуй своё заполненное окружение
и отчёты с телами запросов авторизации.

## Если запуск остановился

- Ошибка о `adminPassword` или `userPassword`: выбери окружение и заполни оба значения.
- Ошибка подключения: проверь, что Gateway запущен, и значение `baseUrl`.
- 401 при входе: проверь пароль demo-пользователя и активный профиль `demo` у Booking.
- 401 после входа: проверь, что все проверяющие JWT сервисы используют публичный ключ,
  соответствующий приватному ключу Booking.
- 503: дождись регистрации Hotel и Booking в Eureka и обновления маршрутов Gateway.
- 409 в запросах, где ожидается другой код: открой ответ и первую красную проверку;
  в запланированных проверках конфликтов 409 должен давать зелёные Tests.

Это последовательный HTTP-сценарий. Конкурентные запросы, перезапуски и внедрение сетевых
сбоев проверяются Java/JUnit/Failsafe-тестами проекта.

Коллекция проверена Newman 6.2.1 на четырёх запущенных JVM: два последовательных запуска,
136 запросов, 466 проверок, 0 ошибок. Сервисы собраны из исходников, соответствующих main
`731f558`. Ожидание подтверждения и отмены дополнительно проверено на контролируемых
HTTP-ответах с промежуточными состояниями.
