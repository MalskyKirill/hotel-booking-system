# Тестирование: JUnit и MockMvc

Все проверки написаны на Java 21 с JUnit Jupiter. Для HTTP-контроллеров используется
MockMvc с включёнными security-фильтрами. Системные тесты выполняются JUnit через
Maven Failsafe на четырёх настоящих Spring Boot приложениях.

## Команды

Нужны JDK 21 и Maven 3.9+. Из корня репозитория:

```sh
# Модульные и интеграционные проверки, включая MockMvc
mvn -B -ntp clean verify

# Полный прогон: предыдущие проверки, исполняемые JAR и системные тесты
mvn -B -ntp -Psystem-tests clean verify
```

Профиль system-tests добавляет [отдельный тестовый модуль](../system-tests/pom.xml)
и упаковку четырёх сервисов в исполняемые JAR на фазе package. Failsafe запускает
BookingSystemIT после сборки сервисов, на фазе integration-test, и проверяет
результаты на verify. Surefire запускает обычные *Test, Failsafe — *IT.
При сбое любой проверки команда verify завершается с ошибкой.

Системный прогон использует отдельный локальный стек: Gateway 19080, Eureka 19081,
Hotel 19082, Booking 19083 и тестовый HTTP-прокси 19084. Все слушатели привязаны к
127.0.0.1. Чтобы изменить весь диапазон:

```sh
mvn -B -ntp -Psystem-tests -Dsystem.base-port=20080 verify
```

Стенд сам создаёт RSA-пару средствами JCA, случайные demo-пароли и тестовые данные.
Обе БД явно заданы как H2 in-memory аргументами запуска; настройки datasource из
окружения не перенаправляют тесты на другую БД. После тестов, включая ошибку,
останавливаются принадлежащие стенду процессы и удаляются временные ключи.
Shutdown hook выполняет ту же очистку при завершении тестовой JVM.

## MockMvc

BookingApiIntegrationTest поднимает Spring-контекст Booking, реальную H2 и
настоящую JWT-аутентификацию. Регистрация и login проходят через MockMvc, создают
пользователей и выпускают подписанные токены. Подменяется только HTTP-граница
HotelReservationClient. Проверяются:

- создание, повтор requestId и ровно один внешний reserve/confirm;
- изоляция истории, чтения и отмены по владельцу;
- идемпотентная отмена и сохранённое состояние CANCELLED;
- компенсация бизнес-отказа и общий ответ 409 BOOKING_CANCELLED;
- валидация и отказ SERVICE-роли до создания записи и внешних вызовов;
- доступность OpenAPI/Swagger, JWT-схема и ответы Saga в спецификации.

HotelApiIntegrationTest использует настоящий Spring-контекст, H2 и проверку RSA
подписи. Проверяет ограничения USER/ADMIN на CRUD, сохранение/удаление гостиницы,
доступность OpenAPI и исключение внутренних маршрутов. Существующие MVC-срезы,
тесты JPA, конкуренции и координатора Saga также сохранены.

## Системные тесты JUnit

[BookingSystemIT](../system-tests/src/test/java/ru/mephi/system/BookingSystemIT.java)
обращается к Gateway через Java HttpClient. Пользовательские JWT выдаёт обычный
login. SERVICE JWT с временным ключом применяется только для сверки состояния Hotel.
Каждый сценарий создаёт собственную гостиницу и номера; тесты выполняются
последовательно, конкурентные запросы внутри сценария синхронизированы барьером.

| Проверка | Ожидаемый результат |
|---|---|
| Права и ошибки | Общий JSON для 400/401/403/404, SERVICE не читает каталог, внутренний API скрыт Gateway, H2 Console выключена |
| Жизненный цикл | CONFIRMED в обоих сервисах, стабильный ID, защита владельца, отмена освобождает номер, соседние даты свободны |
| Один requestId, 32 запроса, ручной режим и авто | Одна запись Booking и timesBooked=1 |
| Один номер, 8 разных ключей | Одно подтверждение, семь отмен, нет лишних HELD; загрузка за две ночи — 100% |
| Автоподбор, 8 запросов | Три разных доступных номера заняты, пять операций отменены; недоступный четвёртый номер исключён |
| Потерянные ответы reserve | Успешные HELD компенсируются в RELEASED, счётчик не увеличивается |
| Потерянные ответы confirm, ручной режим и авто | Уже сохранённый CONFIRMED восстанавливается без лишнего увеличения timesBooked |
| Настоящие read timeout и поздний reserve | RELEASED-маркер создаётся до запоздавших запросов; HELD не появляется повторно |
| Недоступность, ручной режим и авто | 202 PENDING; после восстановления транспортного пути планировщик завершает компенсацию без нового POST |
| Отмена при недоступности | 202 с cancellationRequested; планировщик доводит Hotel и Booking до RELEASED/CANCELLED |
| Потерянные ответы cancel | Итог сверяется по RELEASED и фиксируется CANCELLED |
| Swagger через Gateway | UI загружается, обе спецификации доступны, JWT описан, внутренние маршруты исключены |
| Сквозной traceId | Один X-Correlation-Id виден в Gateway, Booking, Hotel и ECS-логах; у параллельных запросов независимые ID |
| Отказы Gateway до маршрутизации | 401/403, общий ApiError и traceId; HTTP-прокси подтверждает отсутствие вызова Hotel; прямые обращения к бизнес-сервисам также проверяют JWT |
| Корреляция ошибок | 401 и 400 сохраняют ID в ответе и логах; валидация не вызывает Hotel |
| Circuit Breaker и восстановление | OPEN блокирует HTTP-вызовы; PENDING и намерение отмены сохраняются; HALF_OPEN/CLOSED и завершение компенсации подтверждаются логами и обеими БД |

С параметризацией ручного режима и автоподбора получается 20 JUnit-тестов.
Цепь остаётся включённой со штатными параметрами. Перед каждым сценарием стенд
проверяет здоровый путь создания/отмены через публичный API и заполняет окно
успешными вызовами, чтобы ошибки предыдущего теста не влияли на следующий.
При восстановлении GET только читает запись и не запускает Saga; повтор POST
проверяется после терминального состояния.

Hotel публикует в Eureka адрес локального Java HTTP-прокси. Прокси пересылает
запросы в настоящий Hotel и выборочно возвращает 503 до пересылки, теряет ответ
после завершения операции либо удерживает reserve до записи RELEASED-маркера.
Проверяется, что при потере ответа каждая затронутая операция получила 200 от Hotel
до разрыва соединения. Прикладная бизнес-логика и БД не подменяются.
Штатные таймауты клиента Booking (read timeout 5 секунд), число попыток и backoff
сохранены; сокращены интервалы обновления Eureka и запуска планировщика.

## Отчёты и CI

Surefire сохраняет XML и текстовые отчёты в target/surefire-reports сервисов
и общего модуля request-context. Этот модуль также проверяет в MockMvc допустимые,
некорректные и повторённые заголовки, ERROR/ASYNC dispatch, восстановление MDC
при ошибке и исходящий RestClient. Корреляция фонового восстановления проверена
отдельным JUnit-тестом и по HTTP/логам в системных сценариях.
Системные результаты находятся в system-tests/target/failsafe-reports, логи четырёх
JVM — в system-tests/target/stack-logs/run-*/. Токены, пароли и приватные ключи стенд
в отчёты не записывает. Обычный полный прогон занимает несколько минут; время
зависит от машины и загрузки зависимостей Maven.

[GitHub Actions](../.github/workflows/verify.yml) выполняет одну команду Maven с
профилем system-tests для PR и push в main; доступен ручной запуск. Surefire,
Failsafe и логи сохраняются как verification-reports на 7 дней.

Серии по 8 и 32 запроса проверяют инварианты при конкуренции на одном экземпляре
каждого сервиса. Они не задают производственный RPS/SLA и не подтверждают
горизонтальное масштабирование. При имитации сбоев обе H2 остаются живыми;
восстановление после перезапуска с потерей in-memory БД не заявляется.

См. [Saga](booking-saga.md), [автоподбор](room-selection.md),
[контракт API](api-errors-security.md) и [Swagger/OpenAPI](openapi.md).


## Повторные конкурентные серии автоподбора

Сценарий repeatedConcurrentWavesUseAllRoomsBeyondCandidateBatchWithoutIdleSlots
создаёт 33 номера, один выводит из эксплуатации и выполняет три серии по 32
одновременных бронирования на одинаковые даты через Gateway. После каждой серии:

- все 32 доступных номера подтверждены по одному разу, лишних HELD нет;
- восемь повторных POST возвращают прежние ID без увеличения timesBooked;
- Hotel и Booking согласованы, статистика показывает по одному подтверждению;
- отмена освобождает все номера, сохраняет счётчики, следующая серия использует их снова.

Итог — 96 разных подтверждений, у каждого доступного номера timesBooked=3,
у недоступного — 0. Проверяется каталог больше стандартной порции в 20 кандидатов.
Время серии выводится в отчёт Failsafe, но RPS/latency не являются хрупкими
порогами успешности: ограничено общее время теста, проверяются бизнес-инварианты.
Это воспроизводимая проверка заданной конкуренции, не production SLA и не
длительный стресс-тест. Масштабирование на несколько экземпляров не заявляется.

Отдельный JPA-тест AutoReservationContentionTest фиксирует момент конкурентной
записи между поиском первой порции и первой блокировкой. БД, SQL и транзакции
реальные; spy контролирует только момент записи. Два варианта проверяют переход
по курсору при равных и разных timesBooked. До исправления оба воспроизводили
NO_AVAILABLE_ROOM при наличии третьего свободного номера.


## Security-фильтры Gateway

GatewaySecurityTest использует настоящий NimbusJwtDecoder и временную RSA-пару.
Проверяются подпись, issuer, истечение JWT, USER/ADMIN/SERVICE и неизвестные роли,
публичные register/login и Swagger, защита административных маршрутов и actuator.
Разрешённые запросы доходят до маршрутизации (без обнаруженного backend — 503),
запрещённые завершаются 401/403 до неё. Проверяются общий контракт и корреляция.
Закрытые ключи и JWT тестов не выводятся; имена параметризованных тестов с JWT
не содержат значения аргументов.

Системный стенд передаёт отдельный временный публичный ключ также в Gateway.
Готовность проверяется не только отказами 401, но и загрузкой обеих спецификаций
через Eureka, чтобы ранняя готовность security-фильтров не скрывала неготовый
backend. Сквозные проверки подтверждают отсутствие Hotel-вызовов при отказе
Gateway и самостоятельную защиту Booking/Hotel при прямом обращении.

## Отсутствие экземпляра в discovery

HotelDiscoveryUnavailableIntegrationTest поднимает Booking с реальными H2,
JWT и Spring Cloud LoadBalancer, без HTTP-мока. Eureka отключена, поэтому
SimpleDiscoveryClient не содержит Hotel. До исправления оба варианта
воспроизводили необработанный IllegalStateException. После нормализации на
HTTP-границе ручная/автоматическая Saga возвращает 202/PENDING, повтор сохраняет
ID, отмена сохраняет cancellationRequested. Circuit Breaker отключён в этом
изолированном контексте для независимости двух вариантов; его включённое
поведение сохраняют отдельные и системные тесты.
