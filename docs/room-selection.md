# Поиск и автоматический выбор номера

## Свободные номера

`GET /api/rooms` и `GET /api/rooms/recommend` требуют ISO-даты `startDate` и
`endDate`, например:

```
/api/rooms/recommend?hotelId=1&startDate=2027-01-01&endDate=2027-01-03
```

`hotelId` необязателен. Начало должно быть раньше конца; неполные или неверные
даты дают 400. Интервал полуоткрытый `[startDate,endDate)`, соседние заезды не
конфликтуют. Исключаются номера с `available=false` и пересечениями HELD/CONFIRMED.
RELEASED не занимает даты. Рекомендации упорядочены по `timesBooked ASC, id ASC`.

## Создание бронирования

Ручной выбор сохраняет прежний контракт. Для автоподбора:

```json
{
  "autoSelect": true,
  "hotelId": 1,
  "startDate": "2027-01-01",
  "endDate": "2027-01-03",
  "requestId": "unique-operation-key"
}
```

`hotelId` необязателен: без него рассматриваются все отели. При autoSelect=true
переданный roomId игнорируется, включая его участие в сравнении повторного
запроса. При autoSelect=false (значение по умолчанию) нужен положительный roomId;
hotelId в этом режиме игнорируется. Даты, владелец, режим и фильтр отеля входят в
проверку идемпотентности. Менять их с прежним requestId нельзя.

Ответы Saga: 200 CONFIRMED, 202 PENDING, 409 CANCELLED. В PENDING до получения
ответа Hotel и в CANCELLED без найденного номера roomId может быть null.
Полученный от Hotel номер сохраняется в Booking до подтверждения и больше не
меняется при повторе или восстановлении.

## Конкуренция и компенсация

Hotel выбирает кандидатов по загрузке и повторно проверяет каждого под
PESSIMISTIC_WRITE. Каждый кандидат обрабатывается в отдельной короткой
транзакции: не удерживается цепочка блокировок разных номеров. Если кандидат
занят конкурентным запросом, проверяется следующий. Число кандидатов ограничено
`hotel.auto-selection.candidate-limit` (по умолчанию 20, допустимо 1–100).
Если за этот проход номер не найден, возвращается конфликт NO_AVAILABLE_ROOM.

Операция автоподбора хранится отдельно от резерва и блокируется по bookingId.
Это обеспечивает один выбор при параллельных повторах. Версия записи защищает
конкурентное создание операции. Подтверждение увеличивает timesBooked один раз.
Терминальная отмена может быть сохранена до выбора номера: запоздавший reserve
видит RELEASED и не создаёт HELD. Компенсация не освобождает CONFIRMED.

Внутренний API (только SERVICE JWT) принимает bookingId, hotelId и даты:

- POST `/internal/auto-reservations` — выбрать и резервировать;
- POST `/internal/auto-reservations/confirm` — подтвердить;
- POST `/internal/auto-reservations/release` — компенсировать;
- POST `/internal/auto-reservations/status` — прочитать состояние.

Эти маршруты не публикуются через Gateway. После таймаута Booking читает
состояние той же операции, сохраняет найденный номер и продолжает подтверждение
либо компенсацию по правилам [Saga](booking-saga.md). Если номер ещё неизвестен,
восстановление использует сохранённые режим, фильтр отеля и даты.

Данные операции и резерва находятся в H2 in-memory и теряются при остановке
процесса. Это ограничение учебной конфигурации сохраняется.
