# ADR 004. Идемпотентность и конкуренция

Статус: принято. Дата фиксации: 2026-11-02.

## Контекст

Клиент, retry и планировщик повторяют запросы, включая параллельные вызовы.
Повтор не должен создавать второй резерв или увеличивать timesBooked дважды.

## Решение

Booking имеет глобальный UNIQUE(request_id). Повтор сверяет владельца, даты,
режим и применимые roomId/hotelId. Несовпадение возвращает 409. Hotel использует
bookingId как уникальный ключ резерва и PK операции автоподбора. Блокировки строк,
локальные транзакции, UNIQUE и @Version защищают разные участки протокола.

timesBooked увеличивается только при первом переходе в CONFIRMED. Отмена счётчик
не уменьшает; RELEASED остаётся терминальным маркером. Новый запрос после отмены
использует новый requestId. Общая корреляция не заменяет ключ идемпотентности:
requestId — ключ клиентской операции, bookingId связывает Saga, traceId связывает
конкретный HTTP-вызов/фоновую попытку.

## Последствия

Параллельные одинаковые ключи возвращают один ID; разные ключи на пересекающиеся
даты разрешаются проверкой под блокировкой номера. Маркеры хранятся вместе с
историей без TTL; очистка потребует отдельного решения. Бизнес-идемпотентность
не равна гарантии exactly-once доставки HTTP. [Системные проверки](../system-verification.md).
