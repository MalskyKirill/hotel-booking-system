# Бронирование и восстановление Saga

`POST /api/bookings` принимает прежний `requestId` и параметры номера/дат.
Booking фиксирует `PENDING`, затем вне транзакции БД вызывает Hotel.
`HELD` подтверждается в Hotel, после чего локальная транзакция фиксирует
`CONFIRMED`. Повтор с теми же параметрами использует тот же `bookingId`;
другие параметры или владелец приводят к конфликту идемпотентности.

## Ответы API

| HTTP | Статус Booking | Значение |
|---|---|---|
| 200 | CONFIRMED | Обе стороны подтвердили бронирование |
| 202 | PENDING | Результат ещё неизвестен; операция сохранена для восстановления |
| 409 | BOOKING_CANCELLED | Общий ответ ошибки: fields.bookingId указывает отменённую операцию |

Успешное тело (200/202) содержит `id`, `roomId`, даты, статус и время создания.
При отмене POST возвращает ApiError с кодом BOOKING_CANCELLED и fields.bookingId;
полное состояние CANCELLED можно прочитать через GET /api/bookings/{id}. Повтор POST с тем же
`requestId` не создаёт новую запись; итог доступен через GET по ID и историю бронирований.
Обычные ошибки валидации, авторизации и конфликта ключа сохраняют свой формат.

## Ошибки и компенсация

Неопределённые результаты (сеть, таймаут, 5xx, некорректный ответ) повторяются
с ограничением числа попыток и удвоением интервала, максимум до 2 секунд.
Бизнес-отказы, 401/403 и остальные 4xx автоматически не повторяются.
Каждый HTTP-вызов имеет connect timeout 2 секунды и read timeout 5 секунд.

После отказа или исчерпания попыток Booking сначала сохраняет намерение
компенсации (`sagaCompensating`), затем читает состояние Hotel:

- CONFIRMED: восстанавливает локальный CONFIRMED, не освобождает резерв;
- RELEASED: сохраняет CANCELLED;
- HELD или отсутствующая запись: вызывает release с исходными параметрами.

Release сохраняет RELEASED-маркер даже до появления резерва, поэтому поздний
reserve не создаёт HELD. Если confirm выигрывает гонку с release, Booking
повторно читает Hotel и восстанавливает CONFIRMED. При неизвестном результате
компенсации сохраняется PENDING, а не преждевременный CANCELLED.

Если локальная фиксация CONFIRMED не удалась после успеха Hotel, восстановление
использует тот же bookingId и идемпотентные вызовы. Подтверждённый резерв не
освобождается компенсационным release.

## Фоновая обработка

В Booking сохраняются `sagaCompensating`, `sagaNextAttemptAt` и
`sagaRecoveryAttempts`. Обработчик выбирает PENDING и записи с cancellationRequested=true с наступившим временем
попытки. Все сетевые вызовы выполняются вне транзакций БД, а смены состояний —
в коротких транзакциях с блокировкой Booking. Параллельные повторы безопасны
благодаря идемпотентности Hotel и проверкам терминальных состояний Booking.

Новая операция доступна фоновому обработчику через 30 секунд. После отложенной
попытки пауза составляет 5, 10, 20 секунд и далее до максимума 300 секунд.
Обработчик продолжает попытки до терминального результата; постоянная ошибка
доступа требует исправления конфигурации и видна в логах. В одном проходе
обрабатывается ограниченная выборка, сбой одной записи не останавливает остальные.

Настройки `booking.saga`:

| Параметр | По умолчанию |
|---|---:|
| remote.max-attempts | 3 |
| remote.initial-delay-ms | 100 |
| recovery.enabled | true |
| recovery.interval-ms | 5000 |
| recovery.initial-delay-ms | 30000 |
| recovery.batch-size | 20 |

Шаги процесса логируются с bookingId; начало и откладывание Saga также содержат
requestId. Токены и пароли не логируются.

## Проверки и ограничения

Тесты проверяют успех, исчерпание повторов, потерянные ответы reserve/confirm,
сбой release, гонку confirm/release, повторное создание координатора, восстановление
локальной фиксации, выборку по сроку и параллельные запросы.

H2 in-memory теряет данные при остановке процесса. Восстановление работает по
сохранившимся данным; гарантии восстановления после потери самой БД здесь нет.
Для проверки сетевой недоступности без потери данных Hotel можно временно
приостановить и возобновить процесс. Самостоятельная бизнес-отмена уже
подтверждённого бронирования реализована отдельным cancel: см. [историю и отмену](booking-history-cancellation.md).

Системные сценарии с настоящими сервисами выполняются на JUnit/Failsafe;
проверки MVC-слоя — на JUnit/MockMvc: [запуск и отчёты](system-verification.md).

## Circuit Breaker

Booking использует Resilience4j для вызовов Hotel. Circuit Breaker оборачивает
полную последовательность retry: исчерпание повторов считается одним неуспешным
вызовом. Учитываются только неопределённые удалённые результаты (сеть, timeout,
5xx, некорректный ответ). Бизнес-отказы и ошибки 4xx исключены из статистики.

По умолчанию окно содержит 10 вызовов; после минимум 5 наблюдений доля ошибок
50% открывает цепь на 10 секунд. После этого HALF_OPEN разрешает две пробные
операции. Успех закрывает цепь, повторный отказ открывает её. Число одновременных
проб ограничено. Переходы состояний и заблокированные операции логируются с
traceId; события операций также содержат bookingId.

Открытая цепь сразу отклоняет обращение, без дополнительных HTTP-попыток и пауз
retry. Для Saga это неизвестный исход: если status/release/cancel также недоступны,
Booking сохраняет PENDING либо намерение отмены и возвращает 202. Планировщик
продолжает восстановление после закрытия цепи. Ложный успешный откат не фиксируется.

Настройки booking.saga.circuit:

| Свойство | По умолчанию |
|---|---:|
| enabled | true |
| sliding-window-size | 10 |
| minimum-number-of-calls | 5 |
| failure-rate-threshold | 50 |
| wait-duration-ms | 10000 |
| half-open-calls | 2 |

В изолированных JPA-тестах координатора цепь отключена, чтобы накопленные
синтетические ошибки не связывали независимые сценарии. Её состояния, повторы и
ограничение конкурентных проб проверяются отдельными JUnit-тестами; системный
стенд использует включённую цепь.
